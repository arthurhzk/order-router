⏺ The routing rules, in the order to apply them

  Before routing anything

  1. Build each order in full. Fold every order_edited event into its original
     order, so each order is routed once with all of its items. The brief gives
     customers a 30-minute window to add items.
  2. Sort by creation time. Route orders in the order they were created, even if
     the events arrived in a different order.

  For each order

  3. Non-US destination → PARTNER. This is the first check, because
     international orders never use the US warehouses.
  4. No ZIP, or ZIP prefix not in zones.json → PARTNER. The prefix is the first
     three digits. Without a known zone there's nothing to compare warehouses
     on.
  5. Find the warehouses that can take the order. A warehouse qualifies only if:
     - it's enabled, and
     - it has enough available stock for every item in the order. Orders are
       never split.
  6. No warehouse qualifies → PARTNER.
  7. Pick the lowest zone among the warehouses that qualify.
  8. If tied, pick the most days of cover. For each product in the order, days
     of cover is available stock ÷ daily velocity. The order's cover at a
     warehouse is the smallest of those numbers, so the order's tightest item
     decides.
  9. If still tied, use the fixed priority: WH-NJ, then WH-GA, then WH-NV, then
     WH-TX.
  10. Reserve the stock. Subtract the order's quantities from the chosen
      warehouse so later orders see less. PARTNER orders don't touch US stock.

  Output: one line per order with the order number, the warehouse or PARTNER,
  and either the zone or the reason it went to PARTNER.

⏺ It means you shouldn't route an order the moment its order_created event shows
  up. Collect the order's final contents first, then route it once, in the slot
  given by its original creation time.

  Your data has one real case of this:

  - #2041 is created at 13:30:37 with 1× NW-VITD-60, shipping to NV 89117.
  - An order_edited event at 13:48:37 (18 minutes later, so inside the 30-minute
    window) adds 1× NW-MULTI-30.
  - Orders #2042 to #2046 were created between those two events.

  The correct handling: route #2041 once, before #2042, as an order for VITD-60
  + MULTI-30. Its queue position comes from the creation time, and its contents
  come from the final state after edits.

  Wrong ways to handle it:

  1. Route at creation with only VITD-60 and ignore the edit. The added item
     never gets reserved or shipped.
  2. Route twice, once at creation and again at the edit. That breaks "route
     each order once" and can send the order to two warehouses.
  3. Route at the edit time, after #2046. That moves #2041 later in the queue,
     so #2042 to #2046 could use up stock that #2041 should have reserved first.
  4. Treat the added line as a separate shipment. Orders are never split.

  The added item can also change the result. A warehouse that has VITD-60 but
  not enough MULTI-30 no longer qualifies. Days of cover now includes MULTI-30
  too, so a tie could break differently.

  How to implement it: we have the whole day's file, so use two passes.
  1. Group events by order number. Start from each order_created and add the
     addedLines from any edit whose timestamp is within 30 minutes of creation.
  2. Sort the merged orders by creation time and route them in that order.

  Edge cases to decide:
  - Edits after the 30-minute window: ignore them and log a warning.
  - Edits for an order number that was never created: skip them and log a
    warning.
  - The same SKU added again: add it to the existing line's quantity instead of
    creating a duplicate line.

  While checking this I also saw that #2033's ZIP is stored as the number 2134.
  Its leading zero has been lost; it should be 02134. Pad numeric ZIPs back to 5
  digits before taking the 3-digit prefix, otherwise the order wrongly goes to
  PARTNER.

  - Clean: Order (types.ts:47) is the standard shape from earlier: country as a
    string, zip as a 5-digit string or null, cleaned lines, a createdAt date,

  2. index.ts: loading and output

  3. buildOrders.ts: raw events → clean Order[]

     - otherwise → the added lines are appended.
  3. Prepare lines (prepareLines, line 84). Each line's SKU is uppercased and
     lines with quantity ≤ 0 are dropped. Bundles are expanded into their
     components, multiplied by the bundle quantity. addLine merges lines with

  4. Sort by createdAt (line 25). JS sort keeps the original order for ties, so
     equal timestamps stay in file order.

  4. cleanData.ts: the cleaning functions

  - cleanCountry: trims, uppercases, and maps USA / UNITED STATES to US.
  - cleanZip: returns null for an empty or missing ZIP. Numbers are padded to 5
    digits. It then takes the first 5 characters and requires them all to be
    digits.
  - cleanSku: trims and uppercases.
  - findBundle and addLine: catalog lookup and merging same-SKU lines.
